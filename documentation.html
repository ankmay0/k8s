Task Manager on Kubernetes

A small full-stack task app running in a single kind cluster. Its headline feature: the backend authenticates to a separate PostgreSQL database using a Kerberos ticket (GSSAPI) — no database password anywhere.

Repository: github.com/ankmay0/k8s

What this is

Four containers run in one Kubernetes cluster. The frontend serves a React UI; the backend exposes a task API; PostgreSQL stores the tasks; and an MIT Kerberos KDC issues the tickets that let the backend prove its identity to the database. The database and the KDC are kept as separate infrastructure, outside the application project.

Live demo: once deployed, open http://localhost:30080.

Why one cluster? Kubernetes service DNS and the Kerberos/GSSAPI handshake only work within a cluster. Splitting the pieces across multiple clusters breaks both service discovery and authentication — so all four pods share the taskapp cluster.

Kerberos / GSSAPI authentication

This is the core of the project: the backend never sends a password to Postgres. Instead it presents a Kerberos ticket, and Postgres validates it against its own service keytab.

  1. On startup, each pod's init-container contacts the KDC with kadmin (admin credentials) to create its principal and extract a keytab into an in-pod volume. The backend gets backend@TASKAPP.LOCAL; Postgres gets postgres/postgres@TASKAPP.LOCAL.
  2. The backend container runs kinit -k -t /krb/backend.keytab to obtain a Ticket-Granting Ticket, cached at /tmp/krb5cc_0.
  3. The backend connects using the libpq native driver (pg-native). libpq requests a service ticket for postgres/… from the KDC and performs the GSSAPI handshake.
  4. Postgres' pg_hba.conf has method gss for all TCP connections, so it rejects any non-Kerberos login. include_realm=0 maps the principal backend@TASKAPP.LOCAL to the database role backend.
kind gotcha solved here: libpq builds the service principal from the FQDN postgres.default.svc.cluster.local. krb5.conf maps *.svc.cluster.local → TASKAPP.LOCAL and the FQDN service principal is provisioned too, so the realm resolves correctly instead of inventing a bogus cross-realm.

Why a native driver?

Pure-JS node-postgres supports only passwords/SCRAM — it cannot do GSSAPI. The backend therefore uses pg-native (libpq), which requires libpq-dev, libkrb5-dev, build-essential and python3 in the backend image to compile.

Request data flow (add a task)

POST /api/tasks {"title":"..."} nginx (frontend) ──proxy──▶ backend-service:5000 backend ──SQL via libpq (GSSAPI session)──▶ postgres:5432 INSERT INTO tasks (title) VALUES ($1) RETURNING id, title, completed ◀── row ── backend ── JSON ── browser

Task IDs are database-generated (BIGINT GENERATED ALWAYS AS IDENTITY) and persist in a PersistentVolumeClaim, so data survives pod restarts.

Run it

Prerequisites

  • Docker Desktop (running)
  • kind and kubectl on PATH

1 — Create the cluster

cgroup v1 hosts (e.g. Docker Desktop on WSL2 with cgroup v1) must pin an older node image — kind's default needs cgroup v2.
kind create cluster --config k8s-task-app/k8s/kind-cluster.yaml --image kindest/node:v1.30.0

2 — Build & deploy everything

./deploy.ps1

Then open http://localhost:30080.

Configuration

The optional "Login with GitHub" feature needs OAuth credentials. Copy the example and fill it in (never commit the real .env):

cp k8s-task-app/backend/.env.example k8s-task-app/backend/.env

Verify

Pods are healthy

kubectl --context kind-taskapp get pods

The backend holds a Kerberos ticket

kubectl --context kind-taskapp exec deploy/backend -c backend -- klist

Proof: Postgres authenticated the backend via GSSAPI

kubectl --context kind-taskapp exec deploy/postgres -c postgres -- \
  psql -U app -d taskdb -c "SELECT a.usename, g.gss_authenticated, g.principal \
  FROM pg_stat_gssapi g JOIN pg_stat_activity a ON a.pid=g.pid WHERE a.usename='backend';"
usename | gss_authenticated | principal ---------+-------------------+----------------------- backend | t | backend@TASKAPP.LOCAL

gss_authenticated = t confirms the connection used Kerberos, as role backend, with no password.

Persistence

Add a task, delete the backend pod (or the Postgres pod) and reload — the task remains, because it lives in the database's PersistentVolumeClaim, not in the app.

Security notes

Kept out of git

Real secrets are gitignored: .env files (GitHub OAuth secret) and *.keytab. An .env.example documents the required variables with placeholders.

Demo-only credentials

Manifests contain throwaway passwords (admin123, app_password) for local use only. do not reuse them anywhere real.

Keytabs are provisioned at runtime by init-containers, so no Kerberos credentials are ever stored in the repository or baked into images.
